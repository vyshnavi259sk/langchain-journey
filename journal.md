## 2026-11-14
**Day 2: LCEL Runnables — RunnableParallel, RunnableLambda, and RunnablePassthrough**

Day 8 already chained two prompts with the `|` operator, which is LCEL's `RunnableSequence` under the hood. Today's focus is the rest of the Runnable interface that makes LCEL composable beyond a straight line:

- **RunnablePassthrough** — forwards an input (or a sub-key of it) unchanged into a later step, so the original user question can still reach the final prompt even after an intermediate step (like a retriever) has transformed the data.
- **RunnableParallel** — runs multiple branches on the same input at once and merges their outputs into a dict, e.g. `RunnableParallel(context=retriever, question=RunnablePassthrough())`. This is the pattern that later powers RAG chains, where "context" and "question" need to reach the prompt together.
- **RunnableLambda** — wraps a plain Python function as a Runnable so custom logic (formatting, filtering, light post-processing) can sit inside a `|` chain without breaking the interface.

Practical exercise: build a chain that takes a topic string, fans it out with `RunnableParallel` into two branches — one that passes the topic through unchanged and one that wraps a small Python function (`RunnableLambda`) to uppercase it — then merges both into a prompt template before sending to the LLM. This mirrors the shape of a real retrieval chain (`{"context": retriever, "question": RunnablePassthrough()}`) without needing a vector store yet, which is the next topic in the roadmap (document loaders → embeddings → vector stores → retrieval).

## 2026-11-15
**Day 3: Document Loaders — TextLoader, PyPDFLoader, DirectoryLoader, and WebBaseLoader**

With the Runnable interface in hand, the next step in the roadmap is getting real-world data into a chain at all — LangChain's **document loaders**. Every loader returns a list of `Document` objects, each holding `page_content` (the raw text) and `metadata` (a dict with things like `source`, `page`, or any field the loader attaches), so downstream steps (splitting, embedding, retrieval) can rely on one consistent shape no matter where the data came from.

Key loaders covered today:

- **TextLoader** — reads a single plain-text file into one `Document`. The simplest case, useful for confirming the `Document` shape before moving to messier sources.
- **PyPDFLoader** — parses a PDF and returns one `Document` per page, with `metadata["page"]` set automatically. This page-level split matters later: it's a natural, pre-existing chunk boundary that text splitting can respect.
- **DirectoryLoader** — walks a folder and applies a loader (e.g. `TextLoader`) to every matching file via a glob pattern, batching many files into a single list of `Document`s without hand-written loops.
- **WebBaseLoader** — fetches a URL with `requests` and strips HTML with `BeautifulSoup` to produce a `Document`, with `metadata["source"]` set to the page URL. This is the bridge from "my own files" to "the live web" as a data source.

Practical exercise: load three different sources — a local `.txt` file with `TextLoader`, a small PDF with `PyPDFLoader`, and a folder of notes with `DirectoryLoader` — then print `len(documents)` and `documents[0].metadata` for each to compare how metadata differs by loader. This sets up the next topic directly: these raw `Document`s are usually too large to embed as-is, so **text splitting** (e.g. `RecursiveCharacterTextSplitter`) is the next stop before embeddings and vector stores.

## 15-11-2026
**Day 4: Text Splitting — CharacterTextSplitter and RecursiveCharacterTextSplitter**

Day 3's loaders produce `Document` objects, but those Documents are usually far too large to embed or feed into an LLM's context window as-is. Today's topic is **text splitting**: breaking a Document's `page_content` into smaller, slightly overlapping chunks before the next steps (embeddings → vector store → retrieval).

Two key parameters control every splitter:

- **`chunk_size`** — the target maximum size of each chunk (characters, for the splitters used here).
- **`chunk_overlap`** — how many characters repeat between the end of one chunk and the start of the next, so a sentence sitting on a chunk boundary still appears whole in at least one chunk and local context isn't lost.

Splitters covered, both from the standalone `langchain_text_splitters` package (the current recommended import; `langchain.text_splitter` still re-exports them for backwards compatibility):

- **`CharacterTextSplitter`** — splits on a single separator (default `"\n\n"`), only falling back to a hard character cut if a resulting piece is still bigger than `chunk_size`. Simple, but can produce chunks well over the target size if paragraphs are long, and prints a warning when that happens.
- **`RecursiveCharacterTextSplitter`** — tries a *list* of separators in order (paragraph → line → sentence-ish → word → character), recursing into whichever piece is still too big. This is LangChain's recommended default for generic text because it keeps semantically related text together far more reliably than a single fixed separator.

Both expose `split_text(str) -> list[str]` for raw strings and `split_documents(list[Document]) -> list[Document]`, which splits `page_content` while copying the parent's `metadata` onto every resulting chunk — so each chunk still knows which file (and page, for PDFs) it came from, which retrieval will depend on later.

Practical implementation: `day4_text_splitting.py` runs both splitters on the same deliberately "messy" sample text (short title line, one long paragraph, a second paragraph, and a closing line) with identical `chunk_size`/`chunk_overlap` settings and prints each splitter's chunks side by side — `CharacterTextSplitter` produces 4 chunks (two of them over the 220-character target, with a visible warning), while `RecursiveCharacterTextSplitter` produces 7 chunks, all within the target size, by cutting on sentence/word boundaries instead. It then runs `split_documents()` on two sample `Document`s and asserts that `metadata["source"]` survives onto every chunk. The exercise at the end re-runs the comparison with a much smaller `chunk_size=60`, showing both splitters produce far more chunks, with `RecursiveCharacterTextSplitter` still favoring word boundaries where `CharacterTextSplitter` cannot.

No API key or network access is required — this is pure, offline Python. Next up: turning these chunks into embeddings and storing them in a vector database.

## 16-11-2026
**Day 5: Embeddings and Vector Stores**

Day 4 left off with a pile of small text chunks, each still carrying `metadata["source"]`. Those chunks are only useful for *semantic* search once each one is converted into an embedding — a fixed-length vector of floats that places similar meanings close together in vector space — and stored somewhere that can search by similarity instead of exact keyword matching. That's today's pair of concepts: **embeddings** and **vector stores**.

Key pieces:

- **`langchain_core.embeddings.Embeddings`** — the abstract base class every embedding backend (OpenAIEmbeddings, HuggingFaceEmbeddings, etc.) implements. It only needs two methods: `embed_documents(texts) -> list[list[float]]` and `embed_query(text) -> list[float]`. Because every backend shares this interface, a vector store built against one embedding model can be swapped to another without touching any other code.
- **`langchain_community.vectorstores.FAISS`** — LangChain's wrapper around Facebook AI Similarity Search, a local, in-memory vector index with no server and no API key. It exposes `.from_documents()`, `.similarity_search()`, `.similarity_search_with_score()`, `.add_documents()`, and `.as_retriever()`.
- **Why it matters**: this is the index a Retrieval-Augmented Generation (RAG) chain queries at run time instead of relying only on what an LLM memorized during training — and `.as_retriever()` returns a standard LangChain `Runnable`, so it plugs directly into the `RunnableParallel` pattern from Day 2 (`{"context": retriever, "question": RunnablePassthrough()}`) to build a real RAG chain next.

Groq (used for chat in day6.py/day7.py/day8-*.py) doesn't serve an embeddings endpoint, and a real sentence-transformer model would require a large torch download. So today's practical implementation, `day5_embeddings_vectorstore.py`, writes a small custom `Embeddings` subclass, `TfidfEmbeddings`, backed by scikit-learn's `TfidfVectorizer` — a legitimate free/local embedding method with no API key and no network call. It builds a FAISS index from six documents about this same learning journey (day3/day4/day2/day7/day8-1 concepts), runs `similarity_search` and `similarity_search_with_score` against a couple of natural-language queries and confirms the nearest matches are the semantically correct ones, demonstrates `as_retriever().invoke(...)`, and finishes with an exercise that calls `add_documents()` to grow the index after it's already built and re-queries to confirm the new document is retrievable. A commented-out block at the bottom shows the one-line swap to a real API-based `OpenAIEmbeddings` (reading its key via `os.getenv("OPENAI_API_KEY")`) with everything downstream unchanged. `requirements.txt` gained `numpy`, `scikit-learn`, and `faiss-cpu`; no new environment variables were needed since the script runs fully offline.

## 17-11-2026
**Day 6: Retrieval-Augmented Generation (RAG) — wiring a retriever into an LCEL chain**

Day 5 ended with a FAISS vector store whose `.as_retriever()` is just another LangChain `Runnable`, and Day 2 covered `RunnableParallel`/`RunnablePassthrough`, the pieces that fan one input into several branches and merge the results into a dict. Today puts both together to build an actual **Retrieval-Augmented Generation (RAG) chain** — the pattern behind every "chat with your own documents" system.

The core LCEL expression:

```python
rag_chain = (
    RunnableParallel(context=retriever | RunnableLambda(format_docs), question=RunnablePassthrough())
    | prompt
    | llm
    | StrOutputParser()
)
```

Key components and how they fit:

- **`RunnableParallel(context=..., question=...)`** — takes the raw question string and runs two branches on it at once: the retriever turns it into relevant `Document`s ("context"), while `RunnablePassthrough()` forwards the original question unchanged. The results merge into `{"context": ..., "question": ...}`.
- **`RunnableLambda(format_docs)`** — a small custom function wrapped as a Runnable that joins the retrieved `Document` list into a single string, since a prompt template needs text, not Python objects.
- **`ChatPromptTemplate`** — a system message instructing the model to answer *only* from the supplied context (so it doesn't fall back on parametric knowledge), plus the merged dict filling in the human message.
- **`ChatGroq` + `StrOutputParser()`** — generates the grounded answer and unwraps it to plain text, same as day8-1.py.

Why this matters: an LLM's training data is frozen and has no knowledge of documents that only live in a private vector store. RAG fixes that at query time by retrieving the most relevant chunks and stuffing them into the prompt before generation, trading a cheap retrieval step for much better grounding and far less hallucination on domain-specific questions.

Practical implementation: `day6_retrieval_rag.py` rebuilds a Day-5-style `TfidfEmbeddings` + FAISS index over a small knowledge base of facts about this very project (deliberately specific enough that a general-purpose LLM couldn't already know them), then assembles the full `RunnableParallel → prompt → llm → StrOutputParser` chain described above. Since this environment has no `GROQ_API_KEY` configured, the script detects that at chain-build time, skips constructing `ChatGroq` entirely, and instead invokes just the retrieval + prompt-assembly stages — printing the retrieved context and the exact rendered prompt messages that would have been sent — so the LCEL wiring is demonstrated end-to-end without a network call (it still prefers a real answer via Groq when a key is present). The exercise at the end compares `k=1` vs `k=3` on the same query to show how the retriever's `k` controls how much (and how precise) the retrieved context is — the classic recall/precision tradeoff in retrieval. No new dependencies or environment variables were needed; `.env.example` was updated to note that this script also runs correctly without `GROQ_API_KEY` set.

## 18-11-2026
**Day 7: Conversation Memory and Chat History — LangGraph's `StateGraph` + checkpointer**

Day 6's RAG chain answers one question well but has no memory: a follow-up like "what about that?" means nothing to it, because every `.invoke()` is independent. Today's topic is **conversation memory** — carrying prior turns forward so follow-ups work.

The first draft of this used the "classic" LangChain pattern still shown in a lot of tutorials — `RunnableWithMessageHistory` wrapping a chain, backed by `InMemoryChatMessageHistory` — but running it against the version of `langchain-core` installed in this project immediately raised `LangChainDeprecationWarning: RunnableWithMessageHistory is deprecated. Use LangGraph's built-in persistence instead.` So the implementation was rebuilt on the currently-recommended replacement instead:

- **`langgraph.graph.StateGraph` + `MessagesState`** — a tiny graph (here, one node) whose shared state has a `messages` list that *merges* (appends) on every update rather than overwriting, via LangGraph's built-in `add_messages` reducer. A node just returns `{"messages": [new_message]}` and the graph takes care of appending it to the running history.
- **`langgraph.checkpoint.memory.InMemorySaver`** — a checkpointer that saves the graph's state after each step, keyed by a `thread_id` passed in `config={"configurable": {"thread_id": ...}}`. Re-using a `thread_id` on a later `.invoke()` resumes that exact conversation; a new `thread_id` starts a fully isolated one. This is the direct replacement for the deprecated API's `session_id` concept.
- **`trim_messages`** (`langchain_core.messages`, still current/non-deprecated) — caps how many messages actually reach the model on each turn, independent of how much the checkpointer has stored, since history grows forever but a context window (and a token bill) doesn't.

Why it matters: multi-turn memory is table stakes for almost any real LLM product, and LangGraph's checkpointer is also exactly the mechanism the roadmap's later agent/multi-agent topics (Day 31+) are built on — so this doubles as a first, deliberately small look at LangGraph before using it for full agents.

Practical implementation: `day7_conversation_memory.py` compiles a one-node LangGraph app (`call_model` trims history, prepends a system prompt, and gets a reply) with an `InMemorySaver` checkpointer, then demonstrates memory across two turns on one `thread_id` (the second question, "what is my favorite programming language?", only makes sense given the first turn's answer) and proves a second `thread_id` has zero knowledge of the first by calling `app.get_state()` directly against the checkpointer. Since this environment has no `GROQ_API_KEY`, the "respond" step falls back to a deterministic, free, local stand-in (with basic error handling: a live Groq call that raises any exception also falls back to it) rather than skipping the demo, so the full graph/state/checkpointer plumbing still runs end-to-end with no network call — it prefers a real Groq reply whenever a key is present. The exercise re-runs `trim_messages` over a longer 6-message conversation at three different `max_tokens` budgets to show progressively more of the older history getting dropped before the model ever sees it. New dependency: `langgraph` (added to `requirements.txt`); no new environment variables were needed, and `.env.example` / `README.md` were updated to mention the new file.

## 19-11-2026
**Day 8: Conversational RAG — history-aware retrieval with LangGraph**

Day 6 (`day6_retrieval_rag.py`) built a RAG chain that answers one question well, but treats every `.invoke()` as independent — a follow-up that leans on a pronoun ("what about that?") gets embedded and searched exactly as written, with no idea what "that" refers to. Day 7 (`day7_conversation_memory.py`) separately solved multi-turn memory with a LangGraph `StateGraph` + `InMemorySaver` checkpointer, but that graph never retrieved anything. Today combines both into a single **conversational RAG** graph — the "history-aware retriever" pattern from LangChain's own tutorials, rebuilt on LangGraph instead of the deprecated `RunnableWithMessageHistory`.

What the concept is: on every turn, the graph node (1) takes the full message history from the checkpointer, (2) uses a second, small LLM call to rewrite the latest, possibly context-dependent question into a standalone one ("what about that?" → "What does this project's FAISS retriever use to build its vectors? What about that?"), (3) retrieves documents using the *rewritten* question instead of the raw one, and (4) generates the final answer grounded in that retrieved context — then appends the answer as an `AIMessage` so the checkpointer keeps the full thread.

Important components and how they work: `contextualize_question()` is the new piece — an LLM prompt whose only job is reformulating a follow-up using the prior turns, never answering it; it is a no-op on turn one (no history to resolve pronouns against). The retriever and FAISS/TF-IDF index are exactly Day 5/6's, reused unchanged. The `StateGraph`/`MessagesState`/`InMemorySaver` scaffolding is exactly Day 7's, reused unchanged. Both LLM-backed steps (contextualizing, answering) fall back to small deterministic, offline stand-ins when `GROQ_API_KEY` isn't set — the contextualization fallback uses a pronoun heuristic that prefixes the previous question — so the whole graph still runs end to end with no network call.

Why it matters: this is the wiring almost every real "chat with your documents" product uses — RAG and conversation memory are each simple on their own, but a RAG chain with no memory can't handle follow-ups, and a memory-only chat graph (Day 7) never grounds its answers in retrieved facts. Rewriting the query *before* retrieval, rather than only prompting the final answer with history, is what keeps retrieval itself on-topic once a conversation drifts into pronouns.

The practical implementation, `day8_conversational_rag.py`, runs a two-turn demo on one `thread_id` (a question about the FAISS retriever, then the vague follow-up "What about that?") and an exercise that retrieves with the raw follow-up and the rewritten standalone question side by side, reporting whether their top retrieved documents matched or differed. No new dependencies or environment variables were needed — this reuses `langgraph` (Day 7), `langchain-community` + `faiss-cpu` + `scikit-learn` (Day 5), and `langchain-groq` (Day 6), all already in `requirements.txt`.

## 20-11-2026
**Day 9: Tool Calling — binding Python functions to an LLM**

Days 6/8 grounded answers in static, pre-indexed documents via retrieval. Today's topic, **tool calling**, lets the LLM instead request that a specific Python function be run with specific arguments and read back its real result — the mechanism needed for exact computation or live actions, and the direct foundation of agents, coming up next on the roadmap.

Key pieces:

- **`langchain_core.tools.tool`** — a decorator turning a typed, documented Python function into a `StructuredTool`. Its type hints build the tool's argument schema, and its docstring becomes the natural-language description the model uses to decide when (and how) to call it.
- **`ChatGroq.bind_tools(tools)`** — attaches tool schemas to the chat model so a response may come back as an `AIMessage` with `tool_calls` populated (a list of `{"name", "args", "id"}` dicts) instead of plain text.
- **`ToolMessage`** — wraps a tool's real result, keyed to its originating call via `tool_call_id`, and gets appended to the message history before invoking the model again for a final, grounded answer.
- **The manual loop** — `invoke → if tool_calls: run them, append ToolMessages, invoke again → else: done` — exactly what agent frameworks like LangGraph's `create_react_agent` automate internally; writing it by hand once makes clear what such a framework is actually doing.

Why it matters: retrieval (Day 6/8) answers from what was indexed ahead of time; tool calling answers from what the model can compute or fetch right now, deciding per-question whether a tool is even needed — the foundation under every real agent.

Practical implementation: `day9_tool_calling.py` defines four tools (`add_numbers`, `get_word_length`, `safe_divide`, and `search_project_notes` — a deliberately tiny stand-in for wrapping Day 6's real retriever as a callable tool), binds them to `ChatGroq` when `GROQ_API_KEY` is set, and otherwise uses a deterministic offline keyword router so the full call → execute → feed-back loop still runs end-to-end with no network call. The demo covers a single-tool question, a question needing two tool calls in the same turn, and a project-note lookup; the exercise deliberately triggers a `ValueError` in `safe_divide` (division by zero) and confirms the loop catches it and reports the error back as a tool result instead of crashing. No new dependencies — `langchain_core.tools` ships with `langchain-core`, already in `requirements.txt`; no new environment variables either.

## 21-11-2026
**Day 10: Agents — from a manual tool loop to a graph-based ReAct agent with `create_react_agent`**

Day 9 (`day9_tool_calling.py`) wrote the tool-calling loop by hand: `invoke -> if tool_calls: run them, append ToolMessages, invoke again -> else: done`. That loop already *is* a ReAct agent ("Reason, Act, Observe, repeat") — today's topic is wiring that exact loop up as an explicit LangGraph graph, which is what `langgraph.prebuilt.create_react_agent` builds internally, and the direct foundation for every agent/multi-agent topic later in the roadmap (Day 31+).

What the concept is: an agent graph has two nodes in a loop — an "agent" node (the LLM, deciding whether a tool is needed) and a "tools" node (running whatever the LLM asked for) — connected by a conditional edge: if the latest `AIMessage` has `tool_calls`, route to "tools" and then back to "agent"; if not, stop. Important components:

- **`create_react_agent(model, tools, checkpointer=...)`** — a prebuilt `StateGraph` with that agent/tools loop, message-list state, and (given a checkpointer) multi-turn memory via `thread_id`, exactly like Day 7/8's graphs.
- **`langgraph.prebuilt.ToolNode`** — a ready-made node that reads `tool_calls` off the last message, runs each matching tool, and turns any raised exception into an error-flagged `ToolMessage` instead of crashing the graph (with `handle_tool_errors=True`) — the graph-native version of Day 9's manual `try/except`.
- **Conditional edges** — `add_conditional_edges("agent", should_continue, {...})` is the one piece Day 9's plain `while` loop had to spell out imperatively; a graph expresses it declaratively as routing logic.

Why it matters: Day 9 showed what an agent loop actually *does* by writing it manually once; today shows the same loop as the reusable, inspectable graph structure that `create_react_agent` — and everything built on LangGraph from here on — assembles automatically.

Practical implementation: `day10_react_agent.py` defines three new tools (`word_count`, `is_prime`, and `lookup_day_topic` — a structured stand-in for "ask the journal," complementing Day 9's free-text `search_project_notes`), builds a real `create_react_agent` backed by `ChatGroq` when `GROQ_API_KEY` is set, and otherwise hand-wires an equivalent `StateGraph` — same tools, same `ToolNode`, a deterministic keyword-router standing in for the LLM's reasoning step, and the same conditional edge — so the full graph runs end-to-end with no network call. The demo asks one question needing two tool calls in a single turn, then reuses the same `thread_id` for a follow-up to confirm the agent's checkpointer-backed memory still works inside the loop. The exercise deliberately calls `is_prime(1)`, which raises `ValueError`, and confirms `ToolNode` reports it back as an error-flagged `ToolMessage` rather than crashing the graph — the same contract `safe_divide` demonstrated manually in Day 9. No new dependencies (`langgraph.prebuilt` ships with `langgraph`, already in `requirements.txt` since Day 7) and no new environment variables — `GROQ_API_KEY` is reused exactly as in Days 6–9.

## 22-11-2026
**Day 11: Agentic RAG — letting the agent decide whether to retrieve at all**

Day 6 and Day 8 (`day6_retrieval_rag.py`, `day8_conversational_rag.py`) both built RAG pipelines that retrieve on *every* call — retrieval is a fixed pipeline stage with no say in the matter. Day 9 and Day 10 (`day9_tool_calling.py`, `day10_react_agent.py`) separately built tool-calling agents that call Python functions on demand, but neither had a retriever among its tools. Today combines both into **agentic RAG**: the retriever becomes just another `@tool`, and the agent's own reasoning decides, per question, whether retrieval is even relevant — instead of a pipeline that always runs it.

What the concept is: in a non-agentic RAG chain, "retrieve" always executes, whether or not the question has anything to do with the indexed documents. In agentic RAG, retrieval is one tool among several that the model can choose to call, skip, or combine with other tools, exactly like it already chooses among any other tools. This matters because always retrieving wastes a vector search on irrelevant questions and can stuff unrelated "context" into the prompt that actively distracts the model instead of helping it.

Important components and how they work: `retrieve_project_notes(query: str)` is a `@tool`-decorated function that calls `.invoke(query)` on the same `TfidfEmbeddings` + FAISS retriever pattern from Day 5/6/8, but from the agent's point of view it is just a plain string-in/string-out tool like any other. A second, deliberately unrelated tool, `is_palindrome(text: str)`, gives the agent something else to reach for, so the demo can show real tool *choice*, not just a yes/no on the one RAG tool — it raises `ValueError` on an empty string as today's deliberate error case, same contract as `safe_divide` (Day 9) and `is_prime` (Day 10). Both tools are handed to a Day-10-style `create_react_agent`, backed by `ChatGroq` when `GROQ_API_KEY` is set, or an equivalent hand-wired `StateGraph` + `ToolNode` with a deterministic keyword router otherwise — the router's new piece is a "no tool is relevant" branch, since declining every tool and answering directly is itself part of today's topic.

Why it matters: most production "chat with your data" systems are agentic RAG, not a fixed RAG chain, because the agent is usually also expected to answer general questions, run calculations, or call other APIs — a fixed "always retrieve first" pipeline either forces irrelevant context onto those or needs bespoke routing logic bolted on in front of it. Letting the LLM's own tool-calling judgment do that routing is simpler and composes with however many more tools get added later.

Practical implementation: `day11_agentic_rag.py` runs three independent questions, each on its own `thread_id` — one that should trigger `retrieve_project_notes`, one that should trigger `is_palindrome` instead, and one needing no tool at all (simple arithmetic) — printing which tool(s) the agent actually chose for each. The exercise has two parts: it deliberately calls `is_palindrome("")` and confirms the graph reports the `ValueError` as an error-flagged `ToolMessage` rather than crashing, then directly contrasts the agentic approach against a Day-8-style "always retrieve first" pipeline on the palindrome question, printing the irrelevant project context such a fixed pipeline would have forced into the prompt that the agent correctly skipped. No new dependencies (`langgraph`, `langchain-core`, `langchain-community`, `faiss-cpu`, and `scikit-learn` are already in `requirements.txt` from Days 5–10) and no new environment variables — `GROQ_API_KEY` is reused exactly as in Days 6–10, and the full offline run was verified end-to-end today.

## 23-11-2026
**Day 12: Multi-Agent Systems — a LangGraph supervisor routing between specialist agents**

Days 9–11 (`day9_tool_calling.py`, `day10_react_agent.py`, `day11_agentic_rag.py`) all built a single agent choosing among several *tools* inside one `create_react_agent`. That works while every capability lives in one agent's head, but real systems often split responsibilities across separate agents instead, each with its own narrow toolset, coordinated by a **supervisor** that routes each request to the right one. Today builds the simplest version of that pattern: a LangGraph supervisor routing between two specialist agents.

What the concept is: a multi-agent "supervisor" graph has one router node (the supervisor) and one node per specialist. The supervisor classifies the incoming message and a conditional edge sends control to the matching specialist, which runs its own isolated tool-calling loop and returns a final answer. This is a shallow, single-hop version of the handoff pattern used by LangGraph's own multi-agent tooling (`langgraph-supervisor`) — a natural next step once this version is understood is letting a specialist hand control *back* to the supervisor for further routing.

Important components and how they work: `research_agent` is a `create_react_agent` whose only tool is `retrieve_project_notes` (the Day 11 TF-IDF + FAISS retriever tool, rebuilt standalone here); `math_agent` is a second `create_react_agent` whose tools are `add_numbers` and `safe_divide` (Day 9) — the two specialists deliberately share no tools. `supervisor_node` is the new piece: it never calls a tool itself, only classifies the question into `"research"`, `"math"`, or `"direct"` (no specialist needed, e.g. small talk) and stores that in a custom state field, `next`. `SupervisorState(MessagesState)` shows that LangGraph state is just a `TypedDict`, so adding a routing field alongside the message list needed no new machinery.

Why it matters: a single agent's tool list grows without bound as a project takes on more capabilities, and an LLM's tool-selection accuracy degrades as that list grows and tools start to overlap in purpose. Splitting into specialist agents behind a supervisor keeps each specialist's prompt and toolset small, which is how most production "agentic" systems are actually structured once they outgrow a single ReAct loop — the direct foundation for the multi-agent/LangGraph topics later in the roadmap.

Practical implementation: `day12_multi_agent_supervisor.py` builds the supervisor graph with real `create_react_agent` specialists backed by `ChatGroq` when `GROQ_API_KEY` is set, and otherwise swaps in deterministic, offline specialist stand-ins (same tools, same error-handling contract) plus a deterministic keyword classifier, so the whole routing graph runs end-to-end with no network call — verified today in offline mode. The demo routes three questions (one per specialist, one direct) and prints the route chosen each time. The exercise has two parts: it routes a division-by-zero question to the math specialist and confirms `safe_divide`'s `ValueError` surfaces as a handled error instead of crashing the graph, same contract as Day 9/10/11; then it runs five unambiguous sample questions through just the classifier to sanity-check routing accuracy in isolation (5/5 correct offline). **Day 13: Agent Handoffs — direct specialist-to-specialist routing with LangGraph's `Command`**

Day 12 (`day12_multi_agent_supervisor.py`) built a supervisor graph: one central router node classified each question and a static conditional-edge table sent control to exactly one specialist, which always returned straight to `END`. That entry's own closing note flagged the natural next step — letting a specialist hand off without going back through the supervisor first. Today builds that: specialists hand compound questions directly to each other, no central dispatcher revisited in between — the mechanism behind LangGraph's own prebuilt "swarm" multi-agent style.

What the concept is: a LangGraph node function isn't limited to returning a plain state-update dict. It can return a `langgraph.types.Command` object instead, which bundles a state update (`update=...`) *and* a routing decision (`goto=...`) in one value. Day 12 kept those separate — a node returned a dict, and a different conditional-edge function read `state["next"]` to decide where to go. `Command` collapses that: the node that just finished reasoning about a question decides, in the same step, both what happened and what should happen next.

Key pieces: `Command(update={...}, goto="math_agent")` both appends to shared state and transfers control to the `"math_agent"` node — no `add_edge`/`add_conditional_edges` call needed for that hop at all, since the routing lives in the node's own return value. `dispatch_node` still fires once per turn to pick the first specialist (classifying "needs research" / "needs math" / neither), but after that, `research_node` and `math_node` each check whether the *other* half of a compound question is still unanswered and, if so, return `Command(goto=<the other specialist>, ...)` directly. `state["visited"]` is today's deliberate edge case — a cycle guard: each node appends its own name before handing off and refuses to hand off to a name already in that list, so two specialists that would each want to defer to the other stop after one hop instead of looping forever.

Why it matters: a central supervisor is simple but becomes a bottleneck once a question genuinely needs several specialists in sequence — every hop pays a round trip back through the dispatcher. Direct handoffs let specialists compose into a short pipeline for one compound question instead, which is the real building block behind LangGraph's `langgraph-swarm`-style systems and a direct stepping stone toward the advanced multi-agent/LangGraph topics later in the roadmap.

The practical implementation, `day13_agent_handoffs.py`, reuses Day 9/11/12's tools (`retrieve_project_notes`, `add_numbers`, `safe_divide`) behind the same two specialists, backed by real `create_react_agent` + `ChatGroq` when `GROQ_API_KEY` is set and by deterministic offline stand-ins otherwise (verified end-to-end offline today, no network call). The demo runs a research-only question, a math-only question, and a compound question needing both, printing `state["visited"]` each time to show the actual path taken (one hop for the simple questions, two for the compound one, with the supervisor never revisited). The exercise has two parts: dividing by zero inside a mid-turn handoff still reports the error as text instead of crashing, same contract as Day 9/10/11/12; and a question phrased so both specialists' heuristics would want to defer to each other confirms the `visited` cycle guard stops it after one hop each way instead of looping. No new dependencies or environment variables — this reuses `langgraph`, `langchain-core`, `langchain-groq`, `langchain-community`, `faiss-cpu`, and `scikit-learn`, all already in `requirements.txt`, and `GROQ_API_KEY` exactly as in Days 6–12.

## 25-11-2026
**Day 14: Human-in-the-Loop Agents — LangGraph's `interrupt()` for approval workflows**

Day 9-13 all built agents that act immediately the moment they decide to call a tool — fine for a calculator or a read-only retriever, but real agents are often handed *sensitive* tools too ("send this email", "charge this card", "delete this record") where a human should approve the specific call before it executes, not just trust the model's judgement. Today's topic is LangGraph's human-in-the-loop primitive: `interrupt()`.

What the concept is: calling `interrupt(payload)` inside a node pauses the graph entirely — execution stops, `payload` surfaces to whoever is driving the graph (via `result["__interrupt__"]`), and the graph's state is durably checkpointed exactly where it paused. Nothing resumes until the caller later invokes the graph again with `Command(resume=<value>)` on the *same* `thread_id`. The second time that node runs, `interrupt()` doesn't pause again — it returns the resume value instead, as if the call had just taken a very long coffee break.

Important components and how they work: `interrupt()` (`langgraph.types.interrupt`) is the pause/resume point itself. `Command(resume=value)` is what the caller passes to `graph.invoke()` in place of a normal input dict to continue a paused thread. `MemorySaver` (Day 7's checkpointer, reused unchanged) is what makes "pause now, resume later" possible at all — without a checkpointer there's no state to resume *from*. A conditional edge gates which tool calls even reach the approval node: `SENSITIVE_TOOLS` marks `send_notification` as requiring approval while `add_numbers` (Day 9-style) still runs immediately, so human-in-the-loop is opt-in per tool rather than a blanket slowdown on every call.

Why it matters: this is the difference between an agent you can only hand read-only/reversible tools and one you can trust with anything that costs money, sends real messages, or deletes data. `interrupt()` lets the *specific, concrete call* be shown to a human before it executes, while the rest of the agent's reasoning still runs autonomously — the practical answer to "how do agents touch sensitive actions safely," which naturally follows Day 12/13's multi-agent systems now that specialists can reach for real-world tools.

The practical implementation, `day14_human_in_the_loop.py`, builds a small LangGraph agent with two tools: `add_numbers` (safe) and `send_notification` (marked sensitive, a mocked side effect so the demo needs no external API). The agent node is a deterministic keyword router when `GROQ_API_KEY` is unset (same offline-first pattern as every agent day since Day 9/10), or a real `ChatGroq` bound to both tools otherwise; a `human_approval` node calls `interrupt()` only when the agent wants the sensitive tool, approving resumes into the real tool call and rejecting injects a `ToolMessage` saying the action was declined without ever executing it. The demo runs three scenarios on three separate `thread_id`s (a safe call that never pauses, a sensitive call that's approved, a sensitive call that's rejected). The exercise simulates an approver who rejects one sensitive request and then approves a second, different request on that *same* thread, confirming each pending interrupt is handled independently and a rejection doesn't poison later calls or make the agent silently re-attempt the declined action. No new dependencies (`interrupt`/`Command` ship with `langgraph`, already in `requirements.txt` since Day 7) and no new environment variables — `GROQ_API_KEY` is reused exactly as in Days 6-13.

## 26-11-2026
**Day 15: Persistent Checkpointing — LangGraph's `SqliteSaver` for durable state**

Day 7 introduced LangGraph's checkpointer concept via `InMemorySaver`/`MemorySaver`, and Day 14 leaned on it hard: `interrupt()` only works because the checkpointer durably records exactly where a graph paused, so a human can approve or reject a pending action later. But "later" in Day 14 still meant "later in the same Python process" — `InMemorySaver` keeps every checkpoint in a plain Python dict, so the moment the process exits, every paused thread is gone. A real approval workflow needs the service to be allowed to *restart* between "agent asks for approval" and "human approves it" — a deploy, a crash, a scheduled restart — without losing the pending request. Today's topic is LangGraph's **`SqliteSaver`**, a drop-in checkpointer that writes the same checkpoints to a SQLite file on disk instead of to RAM.

What the concept is: a checkpointer is anything implementing LangGraph's `BaseCheckpointSaver` interface — `put`/`get`/`list`, keyed by `(thread_id, checkpoint_id)`. `StateGraph.compile(checkpointer=...)` is the only line that changes between an in-memory graph and a persistent one; the graph logic, `interrupt()`, and `Command(resume=...)` contract from Day 14 are completely unchanged. Swapping the checkpointer is an infrastructure decision, not an application one.

Key components: **`SqliteSaver.from_conn_string(path)`** (`langgraph.checkpoint.sqlite`) is a context manager that opens (and creates, if missing) a SQLite database at `path` and yields a checkpointer backed by it — every `put` LangGraph issues becomes an `INSERT`/`UPDATE` against that file, so the data survives the Python process exiting. **`thread_id`** is still the key every checkpoint is filed under: as long as two processes point `SqliteSaver.from_conn_string` at the same file path and use the same `thread_id`, the second process can resume exactly where the first one paused, even with zero shared memory. **`graph.get_state_history(config)`** walks every checkpoint ever recorded for a thread, which is the basis for LangGraph's "time travel" — replaying or forking from an older checkpoint instead of just the latest one.

Why it matters: this is the gap between "human-in-the-loop looks correct in a demo" and "human-in-the-loop survives a Tuesday-afternoon deploy." Any agent that pauses for approval, runs long enough to outlive a worker process, or needs an audit trail of how its state evolved needs a checkpointer backed by real storage — SQLite here as the simplest durable option, with an identical API available for Postgres (`langgraph.checkpoint.postgres.PostgresSaver`) in production. Because the checkpointer is swapped via one constructor call, nothing else written since Day 7 has to change to make that jump.

The practical implementation, `day15_persistent_checkpointing.py`, builds a tiny three-node "expense approval" graph (`submit -> request_approval -> apply`) that calls `interrupt()` in `request_approval`, structurally identical to Day 14's pattern. It proves persistence by (1) opening a `SqliteSaver` against a file, invoking the graph until it pauses on `interrupt()`, then closing that connection entirely — simulating the first process exiting; (2) opening a brand-new `SqliteSaver` connection against the same file (no Python references back to the first run) and resuming the same `thread_id` with `Command(resume=...)`, which only succeeds because the pending interrupt was read back off disk; and (3) calling `get_state_history()` on the resumed thread to print every checkpoint recorded. The exercise re-runs the same two-process pattern for a *rejected* request on a second, independent `thread_id`, then opens a *third* fresh connection to re-read the first thread's final state, confirming the two threads never cross-contaminate on the shared SQLite file. Verified end-to-end today (ran successfully, output inspected). No new environment variables. New dependency: `langgraph-checkpoint-sqlite`, added to `requirements.txt` (the `langgraph.checkpoint.sqlite` import is not part of the core `langgraph` package already installed since Day 7).
